# ADR-0009 — Convex is an optional membership Mirror, never the source of truth

Status: Accepted · 2026-06-13

Authenticated x.com calls run in the content script; the worker holds no X credentials. It persists browser settings and caches, while a List's membership lives only on X. We want three things that local extension state can't give us: a durable **log** of every add/remove, "already in" marks that are **instant and survive across devices**, and a view of List membership **across the several X accounts** one person operates. We add **Convex** to get them — but as a **Mirror**, not a brain.

The load-bearing decision: **X stays the source of truth; the Mirror only records what we did against X and caches X's answers.** The Mirror never drives X (no reconciler pushing Convex state back to X), and a Mirror failure never blocks or alters the X flow — the assign run, its toast, and undo proceed exactly as today whether or not the write to Convex succeeds. This keeps the existing `XListApi` path untouched and makes the whole feature **additive and optional**: with no device key configured the Mirror is absent (`NullMembershipStore`) and the extension behaves bit-for-bit as before.

Concretely:

- **A new seam, sibling to `XListApi`.** `MembershipStore` has a `ConvexMembershipStore` and a `NullMembershipStore`, chosen by a factory from settings and pinned by a shared contract test. Consumers get live snapshots through `observe`; Convex's one-shot catalog and membership reads stay private to the adapter fallback.
- **Owner checked at the operation boundary.** We read the account logged into x.com before a List run, then read it again after X completes. A changed Owner stops the run or suppresses its Mirror write. The final read and `ownerObservedAt` stamp the **Owner** on the record. No background polling or account registry. ("Account" stays reserved for the *member*; the operator is the **Owner**.)
- **Reconcile is per-author and lazy.** On picker open for one author we mirror X's `memberships.json` answer ("which of my Lists contain this person") into the snapshot — cheap, maps 1:1 onto the existing membership check. We do **not** pull full per-List rosters (paginated, rate-limit-prone, and only needed for a member-browsing screen we aren't building). The snapshot is a lazily-filled (List, stable member identity) presence map. Numeric user ID wins; one tweet ID is a conservative fallback. Handles remain display data and never key cached state.
- **Cross-account is read-only off-session.** The picker groups Lists by Owner from the Convex catalog, but you cannot write to account A's List while logged in as B (X rejects it cross-session). So only the **active Owner**'s Lists are pickable; the rest are shown disabled with a "Switch to @owner" hint, and their "already in" marks come from cached Convex data labelled "as of last use" (we can only freshly reconcile the account currently logged in).
- **The log keeps every outcome.** Each attempt appends one **Audit event**, with its receipt strength. `server-response` add facts are `added | already-member`; remove facts are `removed | already-absent`. Only those direction-matched server facts change a **snapshot**. DOM `ui-state` receipts stay audit-only: checked rows, closed dialogs, and toasts do not prove server state.

This amends one invariant: the extension now holds **exactly one** long-lived credential, the Mirror **device key**, validated by every Convex function (single-tenant, personal store; the deployment is yours). X session tokens remain ephemeral and content-script-only — the device key is unrelated to X auth and grants nothing on X.

Trade-offs accepted. The snapshot can lag X for members added directly on x.com until the next per-author reconcile touches them — acceptable because X's own check still runs for the active Owner and corrects the snapshot, and "already in" is a hint, not a gate. Cross-account checks for a non-active Owner are inherently stale (we can't query X for an account we're not logged into), which is why they're labelled, not trusted. The device key is persisted in worker-owned local Settings and supplied to content when needed; it is not an X credential. The reactive Convex WebSocket remains in content because MV3 workers are short-lived.

Tests must encode "Mirror is optional and never load-bearing": a controller test proves a thrown/rejecting `ConvexMembershipStore` leaves the assign toast, undo, and selection identical to the `NullMembershipStore` run. Convex functions are covered with `convex-test` (recordAssign upserts Owner+List and appends an event; reconcile mirrors `memberships.json` truth including removals; `listsContaining` is reactively correct; a wrong device key is rejected). And `getCurrentAccount` must be **live-verified** against x.com, not just fixtured — reading the wrong account would silently mis-attribute every record, the same fire-and-forget trap the MISSION.md live-verification discipline exists to kill.

## Capacity amendment — 2026-07-22

The live Mirror catalog is bounded: at most **32 Owners**, **384 active Lists** across them, and **256 audit results** per direct mutation. These bounds leave headroom below Convex's 1,000 concurrent I/O operations per function, 4,096 index ranges, and 16 MiB read/write limits per transaction. Persisted external strings use a 256-byte serialized-value cap. Server reads use bounded index scans and reject overflow. They never return a partial catalog. Generation zero reads both legacy missing values and explicit `0` values through the generation index.

`recordAssign` is the only batched seam. The extension sends sequential groups of at most 256 observations, preserving order and every audit event. `replaceCatalog` stays atomic: it rejects a duplicate, oversized, or globally over-capacity catalog before it advances the Owner generation. This cap constrains optional cached data only. X remains authoritative and the extension flow still proceeds if Mirror writes fail.

The bound covers the active working set and per-function work, not total history. Audit events are append-only by design. Retired Lists and snapshots stay unreadable but retained so a List that returns can reuse its last snapshot. Any deletion or expiry policy would change product semantics and needs its own decision.
